# Estoque Multiloja API — Design da v1.1.0

## Objetivo

A versão v1.1.0 evolui a API de estoque para incluir autenticação, usuários, permissões por perfil, vínculo de operadores com lojas e controle de estoque mínimo.

A versão deve preservar as funcionalidades já existentes da v1.0.1 e manter compatibilidade com o MVP atual.

## Escopo

A v1.1.0 incluirá:

- usuários

- autenticação com JWT

- hash seguro de senha

- perfis admin e operador

- vínculo de operador com uma loja

- proteção dos endpoints

- ativação e desativação de usuários

- estoque mínimo por produto e loja

- alerta de estoque baixo

- filtros e consultas relacionadas

- novos testes automatizados

- atualização da documentação

- atualização da versão da API para 1.1.0

Não fazem parte desta versão:

- frontend

- dashboard

- relatórios avançados

- refresh token

- recuperação de senha

- cadastro público

- multiempresa

- pagamentos

- sistema genérico de roles e permissions

## Usuários

Cada usuário terá:

- id

- nome

- email

- senha\_hash

- perfil

- ativo

- loja\_id

O campo email será único.

A senha nunca será armazenada em texto puro.

Usuários não serão excluídos do banco. O administrador poderá ativar ou desativar uma conta.

Usuário inativo não poderá realizar login.

## Perfis

Existirão dois perfis:

### Admin

O administrador terá acesso a todas as lojas e poderá:

- criar usuários

- ativar e desativar usuários

- alterar permissões

- cadastrar, editar e excluir lojas

- cadastrar, editar e excluir produtos

- consultar todos os estoques

- consultar todas as movimentações

- registrar movimentações

- configurar estoque mínimo

- visualizar alertas de estoque baixo

O administrador não precisa obrigatoriamente estar vinculado a uma loja.

### Operador

O operador será obrigatoriamente vinculado a uma única loja.

O operador poderá:

- consultar lojas conforme as regras de acesso

- consultar produtos

- consultar o estoque da própria loja

- consultar movimentações da própria loja

- registrar entradas e saídas na própria loja

- visualizar alertas de estoque baixo da própria loja

O operador não poderá:

- criar usuários

- alterar permissões

- cadastrar, editar ou excluir lojas

- cadastrar, editar ou excluir produtos

- configurar estoque mínimo

- acessar ou movimentar estoque de outra loja

Tentativas de acessar outra loja deverão retornar HTTP 403 Forbidden.

## Primeiro administrador

Não haverá cadastro público de usuários.

O primeiro administrador será criado por um script administrativo executado manualmente.

Exemplo de uso previsto:

python -m app.scripts.create\_admin

Após a criação do primeiro administrador, novos usuários serão cadastrados pela API somente por administradores autenticados.

## Autenticação

O login utilizará email e senha.

Endpoint previsto:

POST /auth/login

Após autenticação válida, a API retornará um access token JWT.

O token terá validade de 60 minutos.

Não haverá refresh token na v1.1.0.

O token será utilizado no padrão Bearer:

Authorization: Bearer <token>

O Swagger deverá permitir autenticação através do botão Authorize.

## Segurança

A senha terá no mínimo 8 caracteres.

As senhas serão armazenadas utilizando hash seguro.

O JWT deverá utilizar uma chave secreta configurada por variável de ambiente.

Nenhuma chave ou senha real será armazenada no repositório.

Erros previstos:

- credenciais inválidas: HTTP 401 Unauthorized

- token inválido ou expirado: HTTP 401 Unauthorized

- usuário inativo: HTTP 401 Unauthorized

- usuário sem permissão: HTTP 403 Forbidden

- operador tentando acessar outra loja: HTTP 403 Forbidden

## Estoque mínimo

O estoque mínimo será configurado por produto e loja.

Cada registro de estoque poderá conter:

- quantidade atual

- estoque mínimo

Exemplo:

quantidade = 3

estoque\_minimo = 5

estoque\_baixo = true

O valor de estoque baixo será determinado quando a quantidade atual estiver menor ou igual ao estoque mínimo.

Somente administradores poderão definir ou alterar o estoque mínimo.

Operadores poderão apenas visualizar o status.

## Consulta de estoque baixo

Será disponibilizada uma consulta específica para itens que atingiram ou ficaram abaixo do estoque mínimo.

Endpoint previsto:

GET /estoques/baixo-estoque

Para administradores, a consulta poderá considerar todas as lojas.

Para operadores, a consulta deverá retornar somente dados da loja à qual o usuário está vinculado.

## Organização do código

A implementação deverá seguir a estrutura atual do projeto.

As responsabilidades serão distribuídas entre:

- app/models

- app/schemas

- app/crud

- app/api/routes

- app/core

Novos módulos deverão manter responsabilidades pequenas e bem definidas.

A autenticação e autorização deverão ser centralizadas em componentes reutilizáveis, evitando regras duplicadas nos endpoints.

## Banco de dados

Serão criadas migrations Alembic para todas as mudanças de estrutura.

Será necessário adicionar a tabela de usuários.

A estrutura de estoque será atualizada para armazenar estoque mínimo por produto e loja.

O vínculo de operadores com lojas deverá utilizar relacionamento com a tabela de lojas.

## Testes

Os 16 testes existentes deverão continuar passando.

Novos testes deverão cobrir pelo menos:

- criação de usuário

- email duplicado

- senha inválida

- login válido

- login inválido

- token inválido

- token expirado

- usuário inativo

- permissões de admin

- permissões de operador

- bloqueio de acesso entre lojas

- configuração de estoque mínimo

- consulta de estoque baixo

- restrições de operador sobre estoque mínimo

Não existe uma meta rígida de quantidade de testes. A prioridade será cobrir corretamente as regras da versão.

## Compatibilidade

A v1.1.0 deve manter as funcionalidades existentes da v1.0.1.

Mudanças de autenticação poderão exigir token nos endpoints protegidos, mas as regras de negócio atuais de lojas, produtos, estoques e movimentações deverão continuar funcionando.

## Deploy

Ao final da versão:

1. todos os testes deverão passar localmente

2. a branch será integrada à main

3. o GitHub Actions deverá ficar verde

4. será criada a tag v1.1.0

5. será criada a GitHub Release v1.1.0

6. a versão será implantada no Render

7. o Swagger em produção deverá exibir 1.1.0

8. autenticação, permissões e estoque mínimo deverão ser verificados em produção

## Divulgação

Após a v1.1.0 estar concluída e implantada em produção, será preparada uma publicação para o LinkedIn mostrando a evolução do projeto da v1.0.1 para a v1.1.0.
